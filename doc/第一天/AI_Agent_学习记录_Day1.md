## 二、今日完成内容

### 1. 最小 Agent 实践

使用 TypeScript + OpenAI SDK 搭建并成功运行了一个最小 Agent。

已实现的工具：

- `getWeather(city)`：查询天气（当前为示例工具）。
- `calculate(expression)`：执行计算。
- `getCurrentTime()`：获取当前时间。

理解并跑通了基本执行流程：

1. 将 system 和 user 消息放入消息历史。
2. 向模型发送请求，并提供可用工具定义。
3. 模型根据上下文决定是否生成工具调用请求。
4. 应用层读取 `tool_calls`，解析参数并分发执行对应工具。
5. 将工具执行结果连同 `tool_call_id` 追加到消息历史。
6. 再次请求模型，由模型根据工具结果继续处理，或生成最终回答。
7. 通过最大循环次数限制 Agent 的执行步数。

**关键理解：** 模型并不会直接执行 TypeScript 函数。模型生成的是结构化工具调用请求，真正执行函数的是应用层 Runtime。

### 2. Day 1 Plus：Agent Runtime 架构设计

今天进一步讨论了如何把最小 Agent 渐进式重构为职责清晰、可扩展的 Runtime。

| 模块 | 核心职责 |
|---|---|
| `Agent` | 管理消息历史、请求模型、处理模型响应、控制循环与终止 |
| `LLMProvider` | 提供统一模型调用接口，隔离 OpenAI、Claude 等供应商差异 |
| `ToolRegistry` | 注册、查询和管理工具定义 |
| `ToolExecutor` | 查找工具、解析参数、校验参数、执行工具并治理超时和异常 |
| `Logger` | 记录结构化运行事件、耗时、状态和错误 |

核心依赖关系：

```text
Agent ───────> LLMProvider
  │
  └──────────> ToolExecutor ───────> ToolRegistry

Agent / LLMProvider / ToolExecutor ───────> Logger
```

设计原则：

- Agent 负责决策与流程控制，不直接执行具体工具函数。
- ToolExecutor 是工具执行的统一治理入口。
- ToolRegistry 只管理工具，不负责执行。
- Agent 依赖统一的 LLMProvider 抽象，不直接绑定某一家模型 SDK。
- Logger 通过依赖注入提供给需要记录运行事件的模块。

### 3. 今日深入讨论的工程机制

- 使用 Zod 对工具参数进行运行时校验。
- 使用 Tool Registry 替代不断扩大的 `switch` 分发逻辑。
- 使用有界并发执行多个工具调用。
- 用 `tool_call_id` 将每个工具结果与模型发出的调用准确关联。
- 处理多个工具调用中部分成功、部分失败的情况。
- 为工具执行设置超时，并区分模型响应结束与 Agent 任务终止。
- 设置最大执行步数等 Runtime 硬性边界。
- 使用结构化日志记录 `runId`、`step`、工具名、耗时、状态、错误、Token 用量和终止原因。

特别明确了两个边界：

1. 模型可以根据工具结果决定业务上的下一步，但 Runtime 必须负责权限、超时、步数、预算等执行安全边界。
2. 模型一次返回多个工具调用，不代表它们一定可以并行执行；如果工具之间存在依赖，就需要串行或分阶段执行。

### 4. 架构知识小测

今天完成了关于以下内容的理解检查：

- Agent 为什么调用 `ToolExecutor.execute()`，而不是直接调用具体工具。
- ToolExecutor 如何通过 ToolRegistry 获取工具。
- 更换模型供应商时，哪些模块可以保持不变。
- LLMProvider 和 LLMResponse 应承担什么职责。
- 多个工具调用中部分失败时，如何把结果反馈给模型并保留 Runtime 的安全控制。

整体回答正确，已具备继续进入工程落地阶段的基础。

## 三、今天形成的关键架构认识

1. **职责分离不是为了拆文件而拆文件。** 模块边界应该由变化原因、职责归属和依赖方向决定。
2. **Agent 决策，Executor 执行。** 这条边界有助于统一治理工具调用。
3. **依赖抽象而不是依赖具体供应商。** 模型供应商变化时，应尽量把变化限制在 Provider 适配层。
4. **模型决策不等于系统安全控制。** 权限、超时、预算、最大步数等必须由应用层强制执行。
5. **工程设计需要考虑失败路径。** 不仅要考虑成功流程，还要考虑未知工具、参数错误、超时、模型异常和部分失败。
6. **并发需要业务语义支持。** 不能仅因为工具调用同时返回，就默认它们彼此独立。

## 五、明日学习计划｜Day 1 Plus 工程落地

明天不重复讲解今天已经掌握的理论，直接基于现有项目逐步改造。

建议顺序：

1. **检查现有项目**：查看目录结构、入口文件、`package.json`、`tsconfig.json` 和当前 Agent 代码。
2. **建立工具契约**：定义 `ToolDefinition` 等类型。
3. **实现 ToolRegistry**：完成注册、查询、获取全部工具和重复注册检查。
4. **实现 ToolExecutor**：统一处理工具查找、参数解析、Zod 校验、执行、超时和错误标准化。
5. **增加并发执行**：实现有界并发，保证每个结果都保留对应的 `tool_call_id`。
6. **抽象 LLMProvider**：把模型请求和供应商 SDK 隔离。
7. **重构 Agent**：让 Agent 通过 Provider 请求模型，通过 Executor 执行工具。
8. **运行与验收**：验证正常调用、未知工具、参数错误、工具超时、部分失败和最大步数限制。

实施原则：

- 渐进式替换，不一次性推翻现有项目。
- 先检查真实代码和依赖版本，再确定类型与 SDK 写法。
- 每次只改造一个清晰的模块边界，修改后立即运行检查。
- 遇到 TypeScript 类型问题，以当前项目安装的 SDK 版本和配置为准。
- 对教学示例中的简化实现进行必要修正，不把示例代码直接视为生产就绪代码。
